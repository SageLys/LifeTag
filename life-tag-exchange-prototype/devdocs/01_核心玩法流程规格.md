# 1. 文档目的

本文档用于把《人生标签交易所：牛马肉铺》的每日经营流程转化为可开发、可测试、可实现的流程规格。

本文档重点回答：

1. 一局从哪里开始，到哪里结束；
    
2. 每一天按什么阶段推进；
    
3. 每个阶段显示什么；
    
4. 每个阶段玩家能做什么；
    
5. 每个阶段系统自动做什么；
    
6. 每个阶段修改哪些运行时数据；
    
7. 什么条件下进入下一阶段；
    
8. 什么条件下胜利、失败、卡住或报错；
    
9. 如何保证 HTML 原型不会变成流程混乱的点击页面。

# 2. 总体流程概览

## 2.1 单局总流程

单局总流程如下：

```text
NewRun
→ InitRunState
→ StartDay(day = 1)
→ Phase_Opening
→ Phase_Purchase
→ Phase_Customer
→ Phase_Draw
→ Phase_Process
→ Phase_Sell
→ Phase_Resolve
→ Phase_Reward
→ StartDay(day + 1)
→ ...
→ EndRun
→ RunReport
```

第 1 天至第 8 天重复每日流程。  
第 8 天收店阶段结束后进入最终结算。

## 2.2 每日 8 阶段

每日流程固定为 8 个阶段：

```text
1. 开店阶段 Phase_Opening
2. 进货阶段 Phase_Purchase
3. 接单阶段 Phase_Customer
4. 抽牌阶段 Phase_Draw
5. 处理阶段 Phase_Process
6. 出售阶段 Phase_Sell
7. 结算阶段 Phase_Resolve
8. 收店阶段 Phase_Reward
```

## 2.3 阶段推进原则

第一版采用半线性阶段推进。

也就是说：

- 玩家按固定顺序经历每日阶段；
    
- 处理阶段和出售阶段可以允许玩家来回查看信息；
    
- 但每日主要阶段不允许倒退；
    
- 收店奖励选择后才能进入下一天；
    
- 第 8 天收店后进入最终结算。


# 4. 单局初始化流程

## 4.1 阶段名称

```text
NewRun / InitRunState
```

## 4.2 进入条件

玩家点击：

```text
开始新局
```

或系统自动创建新局。

## 4.3 系统自动操作

系统创建 RunState：

```text
currentDay = 1
maxDays = 8
cash = 100
totalProfit = 0
targetTotalProfit = 500
reputation = 100
maxReputation = 100
inventory = []
passives = []
activeSupplySources = []
runLog = []
accidentLog = []
dealLog = []
```

系统创建 DeckState：

```text
drawPile = 初始牌组
discardPile = []
hand = []
exhaustPile = []
```

系统载入静态配置：

```text
GameConfig
TagDef
DarkRiskDef
ProductTemplate
CustomerDef
MarketEventDef
CardDef
ShopPassiveDef
SupplySourceDef
BaseActionDef
PricingModeDef
AccidentDef
RewardPoolDef
```

## 4.4 显示内容

初始化后进入主界面，显示：

```text
第 1 / 8 天
现金：100
累计利润：0 / 500
信誉：100
行动点：未开始
库存：0 / 6
```

## 4.5 跳转

初始化完成后自动进入：

```text
DAY_OPENING
```

## 4.6 异常处理

如果配置加载失败：

```text
显示错误：配置数据加载失败。
禁止开始游戏。
```

如果初始牌组为空：

```text
显示错误：初始牌组为空。
禁止开始游戏。
```

# 5. 每日开始流程

## 5.1 阶段名称

```text
StartDay
```

这是每日阶段前的系统准备流程，不是玩家可操作阶段。

## 5.2 进入条件

满足以下任一条件：

1. 新局初始化完成；
    
2. 前一天收店奖励已选择；
    
3. 当前天数小于等于 8；
    
4. 游戏未胜利或失败。
    

## 5.3 系统自动操作

每日开始时：

```text
DayState.dayNumber = RunState.currentDay
DayState.actionPoints = GameConfig.dailyActionPoints
DayState.boughtProductCount = 0
DayState.soldProductCount = 0
DayState.selectedProductId = null
DayState.selectedCustomerId = null
DayState.selectedPricingModeId = null
DayState.currentDealPreview = null
DayState.phase = DAY_OPENING
```

处理库存新鲜度：

```text
对 RunState.inventory 中未售出的商品：
freshnessCurrent -= 1
如果 freshnessCurrent <= 0：
标记为 spoiled
根据后续规则决定是否自动清仓、保留但降价、或增加风险
```

第一版建议：

```text
腐败商品不自动移除。
腐败商品仍可出售，但 basePrice 降低，baseRisk 增加。
```

## 5.4 跳转

进入：

```text
Phase_Opening
```

# 6. 阶段 1：开店阶段 Phase_Opening

## 6.1 阶段定位

开店阶段用于展示今日市场新闻，并建立当天经营环境。

玩家在此阶段主要阅读信息，不做复杂决策。

## 6.2 进入条件

```text
DayState.phase == DAY_OPENING
```

且：

```text
DayState.marketEvent == null
```

## 6.3 系统自动操作

系统生成今日市场新闻：

```text
DayState.marketEvent = generateMarketEvent(RunState, DayState)
```

市场新闻生成需要考虑：

1. 当前天数；
    
2. 已有货源倾向；
    
3. 已获得店铺被动；
    
4. 市场新闻权重；
    
5. 是否为第 4 天中期事件；
    
6. 是否为第 8 天最终日事件。
    

第一版可简化：

```text
从 marketEvents.json 中按权重随机抽 1 条。
第 4 天和第 8 天可以暂时不做特殊事件。
```

写入日志：

```text
第 X 天开店。
今日新闻：[新闻名]
```

## 6.4 显示内容

必须显示：

```text
今日市场新闻标题
今日市场新闻描述
今日市场新闻效果
受影响标签
受影响顾客
受影响风险
```

示例显示：

```text
今日新闻：名校水货事件发酵

效果：
[名校] 售价 +20
[水货] 爆雷 +30
[名校] + [水货] 同时出现时事故等级 +1
履历暗风险区间上限 +20
```

## 6.5 玩家可操作项

玩家可点击：

```text
进入进货阶段
```

可查看：

```text
当前状态栏
库存
牌组概况
已有被动
已有货源倾向
```

不可操作：

```text
买入商品
处理商品
出售商品
选择奖励
```

## 6.6 阶段结束条件

玩家点击：

```text
进入进货阶段
```

## 6.7 状态变化

点击后：

```text
DayState.phase = DAY_PURCHASE
```

## 6.8 异常处理

如果没有可用市场新闻：

```text
使用默认新闻：今日市场平稳。
效果为空。
```

# 7. 阶段 2：进货阶段 Phase_Purchase

## 7.1 阶段定位

进货阶段用于生成今日商品候选，并让玩家选择买入哪些牛马肉。

这是每日第一次重要决策：

```text
今天要用什么素材赚钱？
```

## 7.2 进入条件

```text
DayState.phase == DAY_PURCHASE
```

且：

```text
DayState.marketEvent != null
```

## 7.3 系统自动操作

首次进入进货阶段时：

```text
DayState.productCandidates = generateProductCandidates(
  count = GameConfig.dailyProductCandidateCount
)
```

默认数量：

```text
4 个商品候选
```

商品生成需要考虑：

1. 商品模板权重；
    
2. 当前市场新闻；
    
3. 货源倾向；
    
4. 当前天数；
    
5. 暗风险生成概率；
    
6. 隐藏标签生成规则。
    

每个候选商品生成 ProductInstance，但状态为：

```text
status = candidate
```

## 7.4 显示内容

商品候选区显示 4 个候选商品。

每个商品卡必须显示：

```text
商品名
进价
基础价
基础风险提示，可不显示精确值
新鲜度
显性标签
隐藏标签提示
暗风险提示
买入按钮
```

隐藏标签显示规则：

```text
未揭示隐藏标签显示为 [? 风险类别提示]
```

暗风险显示规则：

```text
无暗风险：暗风险：无
存在但未知：暗风险：存在
已知类别提示：暗风险：履历类可能
```

库存区显示：

```text
当前库存数量 / 库存上限
```

顶部状态栏显示：

```text
现金
累计利润
信誉
行动点
天数
```

## 7.5 玩家可操作项

玩家可以：

1. 选择商品候选查看详情；
    
2. 买入商品；
    
3. 结束进货；
    
4. 查看今日新闻；
    
5. 查看当前库存。
    

## 7.6 买入商品规则

### 前置条件

玩家点击商品候选的“买入”按钮时，必须满足：

```text
RunState.cash >= product.cost
DayState.boughtProductCount < GameConfig.dailyProductBuyLimit
RunState.inventory.length < GameConfig.inventoryLimit
product.status == candidate
```

### 效果

买入成功后：

```text
RunState.cash -= product.cost
product.status = inventory
RunState.inventory.push(product)
DayState.boughtProductCount += 1
从 DayState.productCandidates 中移除或标记已买入
写入日志
```

日志示例：

```text
买入 A号年轻名校肉，花费 40 现金。
```

### UI 反馈

买入后：

```text
现金数值更新
库存区更新
商品候选卡标记为已买入或移除
买入数量更新
```

## 7.7 买入按钮禁用条件

以下情况买入按钮 disabled：

```text
现金不足
今日已达到进货上限
库存已满
该商品已买入
游戏不在进货阶段
```

禁用文案示例：

```text
现金不足，无法买入。
今日进货数量已达上限。
库存已满。
```

## 7.8 阶段结束条件

玩家点击：

```text
结束进货
```

允许玩家 0 买入，但第一版建议给出提示：

```text
你今天没有买入任何商品，可能无法完成最低出售。
是否继续？
```

为了减少流程阻塞，第一版可以允许继续。

## 7.9 状态变化

点击结束进货后：

```text
DayState.phase = DAY_CUSTOMER
```

## 7.10 异常处理

如果商品候选生成失败：

```text
使用默认商品池生成。
```

如果库存满：

```text
允许直接结束进货。
```

如果现金为负：

```text
进入 RUN_FAILED。
```

正常情况下，买入按钮不允许主动导致现金为负。

# 8. 阶段 3：接单阶段 Phase_Customer

## 8.1 阶段定位

接单阶段用于生成今日顾客订单。

这是玩家判断“今天市场需求”的阶段。

## 8.2 进入条件

```text
DayState.phase == DAY_CUSTOMER
```

且：

```text
DayState.productCandidates 已生成
```

## 8.3 系统自动操作

首次进入接单阶段时：

```text
DayState.customerOrders = generateCustomerOrders(
  count = GameConfig.dailyCustomerOrderCount
)
```

默认数量：

```text
3 个顾客订单
```

顾客生成需要考虑：

1. 顾客定义权重；
    
2. 当前市场新闻；
    
3. 当前天数；
    
4. 是否已有店铺被动影响顾客权重；
    
5. 是否已有事故影响顾客预算或风险容忍。
    

第一版可简化：

```text
从 5 类顾客中按权重随机抽取 3 个。
允许重复或不允许重复，需要在配置中指定。
推荐第一版不重复。
```

## 8.4 显示内容

顾客订单区显示 3 个顾客卡。

每个顾客卡显示：

```text
顾客名
预算
风险容忍
喜欢标签
雷区标签
暗风险敏感类型
特殊规则
```

示例：

```text
大厂 HR

预算：220
风险容忍：60

喜欢：
[年轻] [名校] [能加班] [低薪接受]

雷区：
[水货] [维权意识强] [跳槽风险高]

暗风险敏感：
履历风险

特殊规则：
爆雷超过风险容忍时，事故等级 +1。
```

## 8.5 玩家可操作项

玩家可以：

1. 查看顾客详情；
    
2. 点击顾客卡进行选中；
    
3. 查看今日新闻；
    
4. 查看库存；
    
5. 进入抽牌阶段。
    

## 8.6 阶段结束条件

玩家点击：

```text
进入抽牌阶段
```

## 8.7 状态变化

点击后：

```text
DayState.phase = DAY_DRAW
```

## 8.8 异常处理

如果没有可用顾客：

```text
使用默认顾客：创业老板。
```

# 9. 阶段 4：抽牌阶段 Phase_Draw

## 9.1 阶段定位

抽牌阶段用于从经营牌组抽取今日手牌。

它建立当天可用的构筑手段。

## 9.2 进入条件

```text
DayState.phase == DAY_DRAW
```

且：

```text
DayState.customerOrders.length > 0
```

## 9.3 系统自动操作

系统执行：

```text
drawCards(GameConfig.dailyDrawCount)
```

默认抽牌数量：

```text
5 张
```

抽牌规则：

1. 从 drawPile 顶部抽牌进入 hand；
    
2. 如果 drawPile 不足，先将 discardPile 洗入 drawPile；
    
3. 如果 drawPile + discardPile 仍不足，则能抽多少抽多少；
    
4. 临时牌若存在，根据规则加入手牌或抽牌堆；
    
5. 每日开始时上一日手牌应已弃置。
    

## 9.4 显示内容

手牌区显示：

```text
卡牌名
卡牌类型
行动点成本
现金成本
目标类型
效果描述
可用 / 不可用状态
```

牌组信息显示：

```text
抽牌堆数量
弃牌堆数量
手牌数量
```

## 9.5 玩家可操作项

玩家可以：

1. 查看手牌详情；
    
2. 查看牌组数量；
    
3. 进入处理阶段。
    

玩家不可在抽牌阶段打牌。  
第一版推荐所有打牌都放在处理阶段，减少阶段混乱。

## 9.6 阶段结束条件

玩家点击：

```text
进入处理阶段
```

## 9.7 状态变化

点击后：

```text
DayState.phase = DAY_PROCESS
```

## 9.8 异常处理

如果牌组为空：

```text
手牌为空。
允许继续进入处理阶段。
```

如果抽牌过程中出现重复实例 ID：

```text
重新生成 CardInstance.instanceId。
```

# 10. 阶段 5：处理阶段 Phase_Process

## 10.1 阶段定位

处理阶段是每日主要操作阶段。

玩家在此阶段使用：

```text
行动点
现金
基础操作
手牌
店铺被动
```

加工商品、揭示信息、降低风险、提高售价。

## 10.2 进入条件

```text
DayState.phase == DAY_PROCESS
```

且：

```text
DayState.actionPoints == GameConfig.dailyActionPoints
DeckState.hand 已生成
```

## 10.3 显示内容

处理阶段主界面显示：

```text
顶部状态栏
今日市场新闻
库存商品列表
选中商品详情
顾客订单列表
手牌区
基础操作按钮
交易预览区
操作日志
```

## 10.4 玩家可操作项

玩家可以：

1. 选择库存商品；
    
2. 选择顾客；
    
3. 选择定价方式；
    
4. 查看交易预览；
    
5. 使用基础操作；
    
6. 打出手牌；
    
7. 查看店铺被动；
    
8. 查看货源倾向；
    
9. 进入出售阶段。
    

## 10.5 商品选择规则

玩家点击库存商品时：

```text
DayState.selectedProductId = product.instanceId
```

前置条件：

```text
product.status == inventory
product.flags.sold == false
```

选择后自动刷新交易预览。

## 10.6 顾客选择规则

玩家点击顾客订单时：

```text
DayState.selectedCustomerId = customerOrder.instanceId
```

选择后自动刷新交易预览。

## 10.7 定价选择规则

玩家点击定价方式时：

```text
DayState.selectedPricingModeId = pricingMode.id
```

如果所选定价方式不可用，则按钮 disabled。

盲盒价可用条件：

```text
商品存在未揭示隐藏标签
或
商品存在暗风险且暗风险未完全揭示
```

## 10.8 交易预览刷新规则

以下任意变化发生时，系统必须刷新交易预览：

```text
选中商品变化
选中顾客变化
选中定价方式变化
商品标签变化
隐藏标签揭示
暗风险揭示程度变化
包装状态变化
被压制标签变化
临时修正变化
卡牌效果变化
行动点变化
市场新闻变化
店铺被动变化
```

如果缺少商品、顾客或定价方式，交易预览显示：

```text
请选择商品、顾客和定价方式。
```

## 10.9 基础操作：鉴定

### 前置条件

```text
DayState.phase == DAY_PROCESS
selectedProduct != null
```

# 11. 阶段 6：出售阶段 Phase_Sell

## 11.1 阶段定位

出售阶段用于确认交易。

玩家在此阶段完成每日核心收益行为：

```text
选择商品
选择顾客
选择定价
查看预览
确认出售
```

## 11.2 进入条件

```text
DayState.phase == DAY_SELL
```

## 11.3 显示内容

出售阶段显示：

```text
库存商品
顾客订单
定价方式
交易预览
确认出售按钮
返回处理阶段按钮，可选
```

第一版建议允许返回处理阶段，条件是：

```text
尚未进入 DAY_RESOLVE
```

如果允许返回，则流程为：

```text
DAY_SELL → DAY_PROCESS
```

但不能回到抽牌、接单、进货、开店。

## 11.4 出售按钮启用条件

确认出售按钮 enabled 条件：

```text
selectedProduct != null
selectedCustomer != null
selectedPricingMode != null
selectedProduct.status == inventory
selectedProduct.flags.sold == false
DealPreview 有效
```

## 11.5 出售按钮禁用条件

以下情况 disabled：

```text
未选择商品
未选择顾客
未选择定价方式
商品已出售
商品不在库存
定价方式不可用
交易预览计算失败
游戏不在出售阶段
```

## 11.6 确认出售流程

玩家点击确认出售后，系统执行：

```text
1. lock current selectedProduct / selectedCustomer / selectedPricingMode
2. reveal actual hidden risk contribution for settlement
3. reveal actual dark risk contribution if involved in settlement
4. calculate finalPrice
5. calculate finalRisk
6. determine accidentLevel
7. apply accident effects
8. update cash
9. update totalProfit
10. update reputation
11. mark product as sold
12. DayState.soldProductCount += 1
13. create DealResult
14. create AccidentInstance if accidentLevel != none
15. write deal log
16. refresh UI
```

## 11.7 单笔利润计算

第一版采用：

```text
singleProfit =
finalPrice
- product.cost
- accidentRefund
- accidentFine
```

累计利润更新：

```text
if singleProfit > 0:
  RunState.totalProfit += singleProfit
else:
  RunState.totalProfit += 0
```

现金更新：

```text
RunState.cash += finalPrice
RunState.cash -= accidentRefund
RunState.cash -= accidentFine
```

注意：

```text
商品进价已在进货阶段扣除现金。
因此出售时 cash 不再扣 product.cost。
但 singleProfit 需要扣 product.cost，用于计算累计利润。
```

## 11.8 事故弹窗

如果 accidentLevel != none，显示事故弹窗。

事故弹窗必须显示：

```text
事故标题
事故描述
成交收入
退款
罚款
信誉损失
最终爆雷值
事故等级
事故链条
```

## 11.9 无事故反馈

如果 accidentLevel == none，显示普通成交反馈：

```text
成交成功
收入 +X
单笔利润 +Y
累计利润 +Y
爆雷值 Z，未发生事故
```

## 11.10 多次出售

第一版允许每日出售多单。

出售后玩家可以：

```text
继续选择其他商品出售
或
进入结算阶段
```

每日最低出售：

```text
GameConfig.dailyMinimumSaleCount = 1
```

如果 soldProductCount < 1，进入结算阶段时提示：

```text
今日尚未出售任何商品。
是否强制收店？
```

第一版可以允许强制收店，但给予惩罚：

```text
信誉 -5
```

或者不惩罚，只记录日志。  
推荐第一版先不惩罚，避免流程阻塞。

## 11.11 阶段结束条件

玩家点击：

```text
结束出售，进入结算
```

## 11.12 状态变化

```text
DayState.phase = DAY_RESOLVE
```

## 11.13 失败检查

每次出售结算后立即检查：

```text
if RunState.cash < 0:
  phase = RUN_FAILED

if RunState.reputation <= 0:
  phase = RUN_FAILED
```

如果失败，直接进入失败报告，不再继续当日流程。

# 12. 阶段 7：结算阶段 Phase_Resolve

## 12.1 阶段定位

结算阶段用于整理当日状态。

这是系统自动阶段，玩家主要阅读总结。

## 12.2 进入条件

```text
DayState.phase == DAY_RESOLVE
```

且：

```text
游戏未失败
```

## 12.3 系统自动操作

系统执行每日结算：

```text
1. 统计今日成交数
2. 统计今日收入
3. 统计今日单笔利润
4. 统计今日事故
5. 处理今日临时修正过期
6. 处理已售商品移除或标记
7. 处理手牌弃置
8. 处理货源倾向剩余天数
9. 处理每日被动重置
10. 生成 DaySummary
```

## 12.4 商品处理

已售商品：

```text
保持 sold 状态
可从库存列表隐藏
保留在交易日志中
```

未售商品：

```text
留在库存
下一天新鲜度减少
```

第一版中，新鲜度减少在 StartDay 处理。

## 12.5 手牌处理

每日结束时：

```text
将手牌中非临时牌移入 discardPile
临时牌移除
hand = []
```

## 12.6 货源倾向处理

如果 activeSupplySource.durationDays > 0：

```text
durationDays -= 1
如果 durationDays <= 0:
  移除该货源倾向
```

注意：也可以放在 StartDay 处理，但必须统一。  
第一版推荐在结算阶段处理，便于玩家看到“效果还剩几天”。

## 12.7 每日总结显示

结算阶段显示：

```text
今日成交数
今日收入
今日利润
今日事故数
今日信誉变化
当前现金
当前累计利润 / 目标
当前信誉
库存剩余
主要事故原因
```

## 12.8 玩家可操作项

玩家可以点击：

```text
进入收店奖励
```

## 12.9 阶段结束条件

玩家点击：

```text
继续
```

## 12.10 状态变化

```text
DayState.phase = DAY_REWARD
```

## 12.11 失败检查

结算阶段再次检查：

```text
if cash < 0:
  RUN_FAILED
if reputation <= 0:
  RUN_FAILED
```

## 13.1 阶段定位

收店阶段用于提供每日构筑奖励。

```text
DayState.phase == DAY_REWARD
```

```text
游戏未失败
```

## 13.3 系统自动操作

```text
从 RewardPool 中随机抽 3 个。
允许包含现金成本。
现金不足的奖励可显示但不可选。
```

## 13.4 奖励类型

第一版奖励类型至少包括：

```text
add_card
upgrade_card
remove_card
add_passive
add_supply_source
temporary_insurance
gain_cash
gain_reputation
```

其中第一版必须实现：

```text
add_card
add_passive
add_supply_source
```

其他可作为 P1。

## 13.5 显示内容

每个奖励卡显示：

```text
奖励名
奖励类型
费用
描述
稀有度
获得后效果
可选 / 不可选状态
```

示例：

```text

效果：卖给 MCN 时，小事故不扣信誉，改为获得热度。
```

## 13.6 奖励可选条件

奖励按钮 enabled 条件：

```text
RunState.cash >= reward.cashCost
reward.condition 满足
```

如果现金不足：

```text
按钮 disabled
显示：现金不足
```

## 13.7 选择奖励流程

玩家点击奖励后：

```text

写入日志

```

### add_card

```text
将 cardId 对应卡牌加入 discardPile 或 drawPile
推荐加入 discardPile
```

### add_passive

```text
RunState.passives.push(passiveId)
立即生效
```

### add_supply_source

```text
RunState.activeSupplySources.push(supplySourceInstance)

```

### upgrade_card


### remove_card


玩家选择 1 个奖励后，阶段结束。

如果当前不是第 8 天：

```text

```

```text

```

```text
if RunState.cash < 0:
  RUN_FAILED
```

正常情况下现金不足奖励不可选，因此不应主动扣到负数。

# 14. 单局结束流程 EndRun

## 14.1 进入条件

满足任一条件：

```text
RunState.currentDay > GameConfig.runLengthDays
或
第 8 天收店奖励已选择
或
现金 < 0
或
信誉 <= 0
```

## 14.2 胜利判定

如果第 8 天结束时：

```text
RunState.totalProfit >= GameConfig.targetTotalProfit
RunState.cash >= 0
RunState.reputation > 0
```

则：

```text
RunResult = victory
```

## 14.3 失败判定

任一条件满足则失败：

```text
RunState.cash < 0
RunState.reputation <= 0
```

如果第 8 天结束但累计利润不足：

```text
RunState.totalProfit < targetTotalProfit
```

则失败，失败类型为：

```text
profit_target_not_met
```

## 14.4 最终报告内容

最终报告必须显示：

```text

失败原因
最终累计利润
目标累计利润
最终现金
最终信誉
总成交数
总事故数
最大单笔利润
最大事故等级

主要顾客
主要事故原因
获得过的店铺被动
获得过的货源倾向
经营评价文案
```

```text

```


# 16. 事故处理流程

## 16.1 触发时机

确认出售后：

```text
finalRisk = calculateFinalRisk(...)
accidentLevel = getAccidentLevel(finalRisk)
```

如果：

```text
accidentLevel != none
```

则触发事故。

## 16.2 事故等级阈值

```text
0–39：无事故
40–59：小事故
60–79：中事故
80–99：大事故
100+：严重事故
```

## 16.3 事故效果

事故至少修改：

```text
refund
fine
reputationLoss
```

并生成：

```text
accidentTitle
accidentText
accidentChain
```

## 16.4 特殊规则插入点

事故等级确定后，需要检查：

```text
顾客特殊规则
市场新闻特殊规则
卡牌特殊规则
店铺被动特殊规则
```

示例：

```text
如果顾客是大厂 HR，且 finalRisk > customer.riskTolerance，则事故等级 +1。
如果拥有“黑红也是红”，卖给 MCN 时小事故不扣信誉，转为热度。
```

执行顺序建议：

```text
1. 根据 finalRisk 得到基础事故等级
2. 应用顾客特殊规则
3. 应用市场新闻特殊规则
4. 应用卡牌特殊规则
5. 应用店铺被动特殊规则
6. 计算最终退款、罚款、信誉损失
```

# 18. 状态更新原则

## 18.1 单一状态源

所有运行中数据必须以 RunState / DayState / DeckState 为准。

UI 不保存独立游戏逻辑状态。

## 18.2 操作函数原则

所有玩家操作应通过 action 函数修改状态。

示例：

```text
actionBuyProduct(productId)
actionSelectProduct(productId)
actionIdentifyProduct(productId)
actionWashTag(productId, tagId)
actionPackageProduct(productId)
actionUsePR(productId, mode)
actionPlayCard(cardInstanceId, target)
actionSelectPricingMode(pricingModeId)
actionConfirmSell()
actionChooseReward(rewardId)
```

## 18.3 渲染原则

每次 action 后：

```text
更新状态
刷新交易预览
检查失败
重新 render
```

# 19. 异常与防卡死规则

## 19.1 没有商品可买

允许进入下一阶段。

## 19.2 没有库存商品

允许进入出售阶段，但出售按钮不可用。

## 19.3 没有顾客

生成默认顾客。

## 19.4 没有手牌

允许继续处理阶段。

## 19.5 行动点为 0

禁用需要行动点的操作。

## 19.6 现金不足

禁用需要现金成本的操作。

## 19.7 商品已售出

不可再次选择出售。

## 19.8 预览计算失败

出售按钮禁用，并显示错误信息。

## 19.9 阶段错误

如果玩家触发了当前阶段不允许的 action：

```text
不执行操作
显示提示
写入 debug 日志
```

# 20. 流程验收标准

本流程文档对应的开发结果必须满足：

## 20.1 单局验收

1. 点击开始新局后进入第 1 天；
    
2. 第 1 天至第 8 天可完整推进；
    
3. 每天固定经历 8 个阶段；
    
4. 每个阶段都有明确按钮进入下一阶段；
    
5. 第 8 天后进入最终报告；
    
6. 现金低于 0 立即失败；
    
7. 信誉小于等于 0 立即失败；
    
8. 累计利润达到目标且资源条件满足时胜利。
    

## 20.2 每日流程验收

1. 开店阶段生成市场新闻；
    
2. 进货阶段生成商品候选；
    
3. 进货阶段可以买入商品；
    
4. 接单阶段生成顾客；
    
5. 抽牌阶段生成手牌；
    
6. 处理阶段可加工商品；
    
7. 出售阶段可完成交易；
    
8. 结算阶段显示当日总结；
    
9. 收店阶段可选择奖励；
    
10. 收店后进入下一天。
    

## 20.3 交易流程验收

1. 选择商品、顾客、定价后生成预览；
    
2. 未知信息存在时显示风险区间；
    
3. 信息完全时显示精确风险；
    
4. 确认出售后结算收入；
    
5. 确认出售后结算事故；
    
6. 事故链条可见；
    
7. 已售商品不可再次出售。
    

## 20.4 构筑流程验收

1. 每天有手牌；
    
2. 可以打出卡牌；
    
3. 卡牌能修改商品、价格、风险或信息；
    
4. 每天收店奖励可选择；
    
5. 奖励能加入卡牌、被动或货源倾向；
    
6. 现金不足时付费奖励不可选。

# 21. 本文档结论

HTML 原型的核心流程应保持简单、线性、可复盘。

第一版不追求复杂分支流程，而应优先保证：

```text
每日阶段清楚
状态变化明确
玩家操作可控
交易预览可信
事故结算可解释
每日奖励能推动构筑
8 天单局可完整闭环
```

只要该流程稳定成立，后续才能继续扩展数据量、卡牌复杂度、UI 表现、新手引导和 Unity 正式版。
