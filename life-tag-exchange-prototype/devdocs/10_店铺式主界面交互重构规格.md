
## 2.2 RunPhase / DayState.phase 审计

当前已经实现 `RunPhase`，包括：

```text
RUN_INIT
DAY_OPENING
DAY_PURCHASE
DAY_CUSTOMER
DAY_DRAW
DAY_PROCESS
DAY_SELL
DAY_RESOLVE
DAY_REWARD
RUN_END
RUN_FAILED
```

`RunState.phase` 与 `DayState.phase` 同时存在，并通过 `syncPhase()` 同步。

当前问题不是阶段枚举本身，而是：

```text
玩家可见 UI、按钮可用性、内容生成、阶段推进全部强依赖 phase。
```

## 2.3 阶段推进依赖点

当前阶段推进集中在：

```text
src/core/dayFlow.ts
```

核心特征：

```text
NEXT_PHASE 固定定义 DAY_OPENING → DAY_PURCHASE → DAY_CUSTOMER → DAY_DRAW → DAY_PROCESS → DAY_SELL → DAY_RESOLVE → DAY_REWARD。
advancePhase() 负责线性推进。
ensurePhaseContent() 根据当前 phase 自动生成新闻、商品、顾客、抽牌、奖励。
returnToProcess() 只允许 DAY_SELL → DAY_PROCESS。
skipSaleAndResolveDay() 只允许 DAY_PROCESS → DAY_RESOLVE。
```

这部分是旧网页式阶段体验的核心依赖点。

## 2.4 UI 渲染依赖点

当前主渲染入口：

```text
src/ui/render.ts
```

它调用：

```text
renderPhaseGuide(app)
renderMainStageContent(app)
```

当前 `renderMainStageContent()` 根据 `app.state.phase` switch 到不同页面：

```text
renderOpening
renderPurchase
renderCustomer
renderDraw
renderProcess
renderSell
renderResolve
renderReward
renderEnd
```

这说明 UI 仍然是“阶段页面”。本轮必须废弃这个中心结构。

## 2.5 事件绑定审计

当前按钮事件大部分通过 `src/ui/bindEvents.ts` 绑定，再调用 `actions.ts` 或 `dayFlow.ts`。

可保留的部分：

```text

playCard
confirmSell
```

```text
skip-sale-to-resolve
```

# 3. 新交互模型定义

## 3.1 核心原则

玩家不再经历一组网页式阶段页面。

玩家始终停留在一间“牛马肉铺”主界面中，通过点击店内区域触发功能。

旧模型：

```text
看新闻页 → 进货页 → 接单页 → 抽牌页 → 处理页 → 出售页 → 日结页 → 收店页
```

新模型：

```text
主界面是一间店。
玩家点击公告牌、后门货源、订单板、牌盒、砧板、收银台、账本、保险柜等区域。
不同功能在店铺区域中打开。
```

## 3.2 每日阶段的降级处理

每日 8 阶段不再作为玩家可见页面。

它们可以作为内部生命周期、日志标签或兼容状态暂时保留，但不得继续作为 UI 主导航。

废弃玩家可见的按钮：

```text
我知道了，去进货
货已备好，去看订单
订单看完了，抽今日手牌
开始加工
提交成交单
再想想
```

保留硬边界：

```text
开始新局
日结
收店奖励
进入下一天
最终报告
失败报告
```

# 6. ShopZone 与 Action 映射

| ShopZone | 玩家理解 | 首次点击触发 | 重复点击 | 是否强制顺序 |
|---|---|---|---|---|
| news | 看新闻 / 公告牌 | ensureMarketEvent(), openShopArea('news') | 只打开详情，不重刷 | 否 |
| supply | 进货 / 后门货源 | ensureProductCandidates(), openShopArea('supply') | 只查看当日候选 | 否 |
| orders | 接单 / 订单板 | ensureCustomerOrders(), openShopArea('orders') | 只查看当日订单 | 否 |
| deck | 抽牌 / 牌盒 | ensureDailyDraw(), openShopArea('deck') | 不重复抽牌 | 否 |
| inventory | 冷柜 / 库存 | openShopArea('inventory') | 查看库存 | 否 |
| process | 砧板 / 加工 | openShopArea('process') | 加工商品 | 否，但需库存与 AP |
| cashier | 收银台 / 出售 | openShopArea('cashier') | 出售商品 | 否，但需商品、顾客、定价 |
| daybook | 账本 / 日结 | resolveDay() 前确认 | 查看日结摘要 | 是，每天一次 |
| reward | 保险柜 / 收店 | ensureRewardState() | 选择奖励 | 必须日结后 |
| passives | 店铺状态 | openShopArea('passives') | 查看详情 | 否 |

# 8. 功能门控规则

## 8.1 可随时打开

```text
新闻
进货
订单
牌盒
库存
店铺被动
日志
```

## 8.2 可打开但操作受限

```text
砧板：没有库存、行动点不足、现金不足、目标非法时按钮 disabled。
收银台：没有商品、没有顾客、没有定价、预览失败时确认出售 disabled。
```

## 8.3 必须强门控

```text
日结：每天只能结算一次。日结后不得继续进货、抽牌、加工、出售。
收店奖励：必须日结后才能选择。选择并完成后进入下一天或最终报告。
```

# 9. 验收清单

## 9.1 交互验收

```text
玩家进入新局后看到的是店铺场景，不是阶段页面。
点击公告牌可查看新闻。
点击后门货源可生成并查看商品候选。
点击订单板可生成并查看顾客订单。
点击牌盒可抽取今日手牌，重复点击不重复抽牌。
点击砧板可使用鉴定、洗标、包装、公关和卡牌。
点击收银台可选择商品、顾客、定价并确认出售。
交易预览在加工和出售相关区域常驻。
点击账本执行日结。
日结后点击保险柜进入收店奖励。
收店奖励完成后进入下一天或最终报告。
```

## 9.2 回归验收

```text
现金仍是构筑资源，不是胜利目标。
累计利润仍是通关目标。
事故仍由最终爆雷值确定，不使用随机骰子。
普通鉴定仍不能完全揭示暗风险。
未知信息存在时仍显示爆雷区间。
已售商品不能再次出售、加工或出牌作用。
所有 disabled 按钮必须显示原因。
Debug 面板和固定测试局继续可用。
```

## 9.3 技术验收

```text
规则层不得依赖 UI 层。
售价、爆雷、事故计算不得写入 render 文件。
ShopScene / ContextPanel 只显示状态和调用 action。
所有状态修改继续通过 core action 完成。
不得把所有逻辑塞进 render.ts 或 style.css。
```
