# 06_UI页面与交互规格

文档编号：06  
文档名称：UI 页面与交互规格  
项目名称：《人生标签交易所：牛马肉铺》HTML 快速验证原型  
对应策划案版本：核心策划案 v0.5  
文档版本：v0.1  
用途：定义 HTML 原型第一版的页面结构、信息层级、组件规格、交互规则、按钮启用 / 禁用条件、弹窗、状态反馈、日志显示和 UI 验收标准。  
适用对象：游戏设计者、前端开发者、AI Agent / Codex、测试者。

---

# 1. 文档目的

本文档用于把已完成的玩法流程、系统规则、数据结构、内容配置和计算规格，转化为可直接开发的 HTML UI 与交互规格。

本文档重点回答：

1. HTML 原型主界面应该如何布局；
2. 每个阶段显示哪些 UI 区域；
3. 每个组件显示哪些字段；
4. 玩家点击按钮后调用什么交互；
5. 每个按钮什么时候 enabled，什么时候 disabled；
6. 交易预览如何向玩家解释售价、爆雷、未知风险和事故；
7. 事故、奖励、最终报告如何弹出；
8. UI 如何避免泄露隐藏标签和暗风险；
9. UI 如何支持玩家复盘；
10. 第一版做到什么程度算完成。

本文档不负责：

- 编写正式美术风格；
- 设计完整视觉品牌；
- 设计移动端布局；
- 编写最终 CSS 细节；
- 定义最终动画、音效或演出；
- 重新定义系统规则、计算公式和配置数据。

# 2. UI 设计总原则

## 2.1 第一版 UI 定位

第一版 UI 是：

```text
文字 + 卡片 + 面板式策略原型 UI
```

它的首要目标不是美观，而是：

```text
让玩家能理解规则、做出决策、看懂收益、看懂风险、复盘事故。
```

## 2.2 单页应用原则

第一版采用单页界面。

推荐形式：

```text
一个 index.html
一个主 App 容器
多个区域面板
通过 RunState / DayState 变化重绘 UI
```

不推荐第一版做多页面跳转。

原因：

```text
玩家每天需要同时查看：状态、新闻、商品、顾客、手牌、操作、预览和日志。
如果拆成多页面，会增加信息切换成本，不利于验证核心玩法。
```

## 2.3 信息优先级原则

UI 信息优先级从高到低为：

```text
1. 当前局势：天数、现金、累计利润、信誉、行动点
2. 当前阶段：玩家现在该做什么
3. 当前决策对象：商品、顾客、定价
4. 当前交易预览：售价、利润、爆雷、事故
5. 当前可用手段：基础操作、手牌、被动、货源
6. 解释与复盘：breakdown、日志、事故链条
7. 次要文本：风味描述、调侃文案、非必要说明
```

## 2.4 不泄露隐藏信息原则

UI 必须严格遵守信息规则。

未揭示隐藏标签不得显示真实 tagId 或真实中文名。

正确显示：

```text
[?]
[? 履历风险]
未知标签：可能影响爆雷上限
```

错误显示：

```text
[水货]
隐藏标签：水货
未知风险：[水货] +35
```

除非玩家已经通过鉴定或其他规则揭示该标签。

暗风险未完全揭示时，不得显示具体 darkRiskId、具体 actualRiskValue 或完整事故文案。

## 2.5 按钮可解释原则

所有 disabled 按钮都必须给出原因。

推荐方式：

```text
按钮置灰 + hover / 小字提示 disabledReason
```

示例：

```text
洗标 disabled：请选择一个已揭示且可洗的标签。
盲盒价 disabled：该商品没有未知信息，不能使用盲盒价。
买入 disabled：今日进货数量已达上限。
奖励 disabled：现金不足，需要 70 现金。
```

## 2.6 交易预览常驻原则

处理阶段和出售阶段中，交易预览必须常驻。

玩家只要选择了商品、顾客和定价方式，就应该立刻看到：

```text
预计售价
预计利润
爆雷值或爆雷区间
事故预测
主要加价来源
主要风险来源
未知风险来源
出售按钮状态
```

## 2.7 操作后即时反馈原则

任何操作执行后，UI 必须立刻刷新：

```text
状态栏
商品卡
商品详情
顾客卡
手牌区
基础操作区
定价区
交易预览
日志区
```

不得出现玩家操作成功但页面数值不更新的情况。

# 3. 主界面总布局

## 3.1 推荐桌面布局

第一版目标平台是桌面浏览器。推荐宽屏三栏布局。

```text
┌────────────────────────────────────────────────────────────────────┐
│ HeaderStatusBar：第 X/8 天｜阶段｜现金｜累计利润｜信誉｜行动点｜库存｜手牌 │
├────────────────────────────────────────────────────────────────────┤
│ PhaseGuideBar：当前阶段说明 + 下一步按钮 / 阶段推进按钮                  │
├───────────────┬──────────────────────────────┬─────────────────────┤
│ 左栏           │ 中栏                          │ 右栏                 │
│ MarketEvent    │ ProductList / Inventory       │ CustomerOrders       │
│ PassiveSupply  │ ProductDetail                 │ PricingPanel         │
│ RunLog         │ HandCards / BaseActions       │ DealPreview          │
├───────────────┴──────────────────────────────┴─────────────────────┤
│ FooterDebug / optional：抽牌堆、弃牌堆、版本号、重开按钮、Debug 开关       │
└────────────────────────────────────────────────────────────────────┘
```

## 3.2 推荐区域宽度

第一版可采用 CSS Grid。

```text
左栏：22%
中栏：48%
右栏：30%
```

或：

```text
grid-template-columns: 280px minmax(480px, 1fr) 360px;
```

## 3.3 最小可用宽度

桌面浏览器最小建议宽度：

```text
1280px
```

低于 1280px 时可允许横向滚动，不要求第一版做移动端适配。

## 3.4 UI 区域列表

第一版必须实现以下 UI 区域：

```text
AppShell

PhaseGuideBar
MarketEventPanel
PassiveSupplyPanel
ProductCandidatePanel

BaseActionPanel
PricingPanel

ActionLogPanel
AccidentModal

DebugPanel，可选但建议实现
```

# 4. 全局 UI 状态

## 4.1 UIState 建议结构

UI 可以维护独立于 RunState / DayState 的轻量状态。

```text
UIState {
  selectedProductId: string | null,
  selectedCustomerOrderId: string | null,
  selectedPricingModeId: string | null,
  selectedTagId: string | null,
  selectedCardInstanceId: string | null,
  selectedRewardId: string | null,

  expandedPanelIds: string[],
  activeModal: null | "accident" | "reward" | "run_report" | "confirm" | "error",
  activeTooltip: string | null,

  showDebug: boolean,
  logFilter: "all" | "deal" | "accident" | "system",

  lastToastMessage: string | null
}
```

## 4.2 选择状态同步原则

DayState 中已经有：

```text
selectedProductId
selectedCustomerId
selectedPricingModeId
currentDealPreview
```

第一版可以直接使用 DayState 作为选择状态来源。

如果同时存在 UIState 与 DayState，则必须遵守：

```text
DayState 是游戏逻辑真实状态。
UIState 只保存展示状态。
```

不得出现 UI 选中 A 商品，但 DayState.selectedProductId 是 B 商品。

## 4.3 选择清空规则

以下情况需要清空选择：

| 情况 | 清空对象 |
|---|---|
| 进入新一天 | selectedProductId、selectedCustomerId、selectedPricingModeId、selectedTagId、selectedCardInstanceId |
| 商品售出 | 如果售出的是 selectedProduct，则清空 selectedProductId 与 selectedTagId |
| 顾客订单失效 | 如果失效的是 selectedCustomer，则清空 selectedCustomerId |
| 进入 RUN_END / RUN_FAILED | 清空所有可操作选择 |
| 重新开始新局 | 清空全部 UIState |

# 5. 阶段显示矩阵

## 5.1 阶段与主要可见区域

| 阶段 | 状态栏 | 阶段提示 | 新闻 | 商品候选 | 库存 | 商品详情 | 顾客 | 手牌 | 基础操作 | 定价 | 交易预览 | 日志 | 弹窗 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| RUN_INIT | 是 | 是 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 开始新局 |
| DAY_OPENING | 是 | 是 | 是 | 否 | 是 | 可选 | 否 | 否 | 否 | 否 | 否 | 是 | 否 |
| DAY_PURCHASE | 是 | 是 | 是 | 是 | 是 | 是 | 否 | 否 | 否 | 否 | 否 | 是 | 可选确认 |
| DAY_CUSTOMER | 是 | 是 | 是 | 否 | 是 | 是 | 是 | 否 | 否 | 否 | 否 | 是 | 否 |
| DAY_DRAW | 是 | 是 | 是 | 否 | 是 | 是 | 是 | 是 | 否 | 否 | 否 | 是 | 否 |
| DAY_PROCESS | 是 | 是 | 是 | 否 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 是 | 可选确认 |
| DAY_SELL | 是 | 是 | 是 | 否 | 是 | 是 | 是 | 可见不可用 | 可选返回处理 | 是 | 是 | 是 | 事故 |
| DAY_RESOLVE | 是 | 是 | 是 | 否 | 是 | 是 | 是 | 否 | 否 | 否 | 日结摘要 | 是 | 日结提示 |
| DAY_REWARD | 是 | 是 | 是 | 否 | 是 | 可选 | 可选 | 否 | 否 | 否 | 否 | 是 | 收店奖励 |
| RUN_END | 是 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 是 | 最终报告 |
| RUN_FAILED | 是 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 否 | 是 | 失败报告 |

## 5.2 阶段按钮

每个阶段至少有一个主按钮。

| 阶段 | 主按钮 | 按钮行为 |
|---|---|---|
| RUN_INIT | 开始新局 | initRun() |
| DAY_OPENING | 进入进货 | advancePhase(DAY_PURCHASE) |
| DAY_PURCHASE | 结束进货 | advancePhase(DAY_CUSTOMER) |
| DAY_CUSTOMER | 进入抽牌 | advancePhase(DAY_DRAW) |
| DAY_DRAW | 进入处理 | advancePhase(DAY_PROCESS) |
| DAY_PROCESS | 进入出售 | advancePhase(DAY_SELL) |
| DAY_SELL | 结束今日出售 | advancePhase(DAY_RESOLVE) |
| DAY_RESOLVE | 收店 | advancePhase(DAY_REWARD) |
| DAY_REWARD | 选择奖励后继续 | chooseReward() 后 nextDay() 或 endRun() |
| RUN_END / RUN_FAILED | 重新开始 | initRun() |

## 5.3 阶段倒退规则

第一版只允许：

```text
DAY_SELL → DAY_PROCESS
```

条件：

```text
尚未进入 DAY_RESOLVE
```

不允许：

```text
DAY_PROCESS → DAY_DRAW
DAY_DRAW → DAY_CUSTOMER
DAY_CUSTOMER → DAY_PURCHASE
DAY_PURCHASE → DAY_OPENING
```

# 6. AppShell

## 6.1 作用

AppShell 是页面根容器，负责承载所有 UI 区域。

## 6.2 必须包含

```text
HeaderStatusBar
PhaseGuideBar
MainGrid
ModalLayer
ToastLayer
```

## 6.3 UI 状态

AppShell 根据 RunState.phase 决定：

```text
当前显示哪些面板
哪些面板可交互
是否显示弹窗
```

## 6.4 禁止事项

AppShell 不应直接计算售价、爆雷或事故。

它只调用：

```text
render(state)
calculateDealPreview(context)
handleAction(actionType, payload)
```

# 7. HeaderStatusBar 顶部状态栏

## 7.1 作用

顶部状态栏用于常驻显示玩家最关键的经营状态。

## 7.2 显示字段

必须显示：

```text
当前天数 / 总天数
当前阶段
现金 cash
累计利润 totalProfit / targetTotalProfit
信誉 reputation / maxReputation
行动点 actionPoints
库存数量 inventoryCount / inventoryLimit
手牌数量 handCount
```

推荐显示格式：

```text
第 3 / 8 天｜处理阶段｜现金 146｜累计利润 220 / 500｜信誉 82 / 100｜行动点 2｜库存 4 / 6｜手牌 3
```

## 7.3 数值颜色规则

第一版可用简单文字标记，不强制颜色。

推荐规则：

| 字段 | 正常 | 警告 | 危险 |
|---|---|---|---|
| 现金 | cash >= 50 | 0 <= cash < 50 | cash < 0 |
| 累计利润 | 按进度显示 | 第 6 天后低于目标进度 | 第 8 天低于目标 |
| 信誉 | >= 60 | 30–59 | <= 29 |
| 行动点 | >= 2 | 1 | 0 |

显示文本示例：

```text
信誉 24 / 100（危险）
行动点 0（今日已无加工能力）
```

## 7.4 点击行为

第一版可以不做点击行为。

可选：点击累计利润显示目标说明。

## 7.5 验收标准

```text
任意操作改变 cash / totalProfit / reputation / actionPoints 后，顶部状态栏必须同步更新。
不得出现 NaN、undefined、null。
```

# 8. PhaseGuideBar 阶段提示栏

## 8.1 作用

阶段提示栏告诉玩家当前阶段做什么，以及下一步按钮在哪里。

## 8.2 显示字段

```text
阶段名
阶段说明
当前阶段主目标
阶段主按钮
可选警告
```

示例：

```text
处理阶段
用行动点、现金、基础操作和手牌加工库存商品。选择商品、顾客、定价后可查看交易预览。
主目标：至少完成 1 笔出售前的准备。
[进入出售阶段]
```

## 8.3 各阶段说明文案

| 阶段 | 阶段说明 |
|---|---|
| DAY_OPENING | 阅读今日市场新闻，判断今天哪些标签涨价、哪些标签更危险。 |
| DAY_PURCHASE | 从今日候选牛马肉中进货。进货会消耗现金，库存和每日进货数量有限。 |
| DAY_CUSTOMER | 查看今日顾客订单。不同顾客有不同偏好、雷区、预算和风险容忍。 |
| DAY_DRAW | 抽取今日经营手牌。手牌决定今天可以使用哪些包装和手法。 |
| DAY_PROCESS | 加工商品。你可以鉴定、洗标、包装、公关、打出卡牌，并查看交易预览。 |
| DAY_SELL | 确认出售。选择商品、顾客和定价方式后，决定是否成交。 |
| DAY_RESOLVE | 查看今日结算摘要。确认收入、事故、信誉和库存变化。 |
| DAY_REWARD | 选择一个收店奖励。部分强力奖励需要消耗现金。 |

## 8.4 阶段推进确认

以下情况点击阶段推进按钮时需要二次确认：

| 情况 | 提示 |
|---|---|
| 进货阶段 0 买入 | 你今天没有买入任何商品，可能无法完成出售。是否继续？ |
| 处理阶段还有行动点 | 你还有未使用行动点。是否进入出售阶段？ |
| 出售阶段 0 出售 | 今日尚未出售商品，可能浪费一天。是否结束今日出售？ |
| 收店奖励为付费奖励 | 将消耗 X 现金。是否选择该奖励？ |

第一版可使用 ConfirmModal 或浏览器 confirm。

推荐使用 ConfirmModal，方便后续统一样式。

# 9. MarketEventPanel 今日市场新闻面板

## 9.1 作用

显示今日市场新闻和可见规则效果。

市场新闻是每日决策的起点，必须始终可见或易于查看。

## 9.2 显示字段

```text
新闻标题 displayName
新闻正文 newsText
效果摘要 modifiers / specialRules 的 displayText
受影响标签
受影响顾客
受影响暗风险类别
持续时间
```

示例：

```text
今日新闻：名校水货事件发酵

名校标签仍然值钱，但市场开始严查名校水货。

可见效果：
- [名校] 售价 +20
- [水货] 爆雷 +30
- 履历风险上限提高
- [名校] + [水货] 同时出现时，事故等级 +1
```

## 9.3 空状态

如果今日没有市场新闻：

```text
今日市场平稳。
无特殊价格或风险修正。
```

## 9.4 交互

点击市场新闻中的标签名，可选中或高亮相关 TagChip。

第一版可以不做该增强。

## 9.5 验收标准

```text
每日市场新闻生成后必须显示。
市场新闻的所有玩家可见效果必须能在 UI 中读到。
市场新闻不得暴露未揭示商品的具体隐藏标签。
```

# 10. PassiveSupplyPanel 被动与货源面板

## 10.1 作用

显示玩家当前拥有的长期构筑能力。

## 10.2 显示内容

分两组显示：

```text
店铺被动
货源倾向
```

每个条目显示：

```text
名称
简短效果
剩余持续天数，若有
是否本日已触发，若需要
```

示例：

```text
店铺被动：黑红也是红
卖给短视频 MCN 时，小事故不扣信誉，改为热度 +2。

货源倾向：校招剩料
剩余 1 天。更容易刷出年轻、名校、小镇做题家相关商品。
```

## 10.3 空状态

```text
暂无店铺被动。
暂无货源倾向。
```

## 10.4 交互

点击条目展开详情：

```text
完整 description
触发条件
效果摘要
来源：奖励 / 初始 / 事件
```

## 10.5 验收标准

```text
获得被动或货源后，该面板必须立刻更新。
货源倾向过期后不得继续显示为有效。
```

# 11. ProductCandidatePanel 商品候选面板

## 11.1 作用

进货阶段显示今日可购买的商品候选。

## 11.2 显示时机

只在以下阶段完整显示：

```text
DAY_PURCHASE
```

其他阶段可以隐藏，或显示“今日候选已结束”。

## 11.3 商品候选卡 ProductCandidateCard

每张候选卡显示：

```text
商品名
进价 cost
基础价 basePrice
基础风险提示，可显示为“基础风险：低 / 中 / 高”或数值
新鲜度 freshnessCurrent / freshnessMax
显性标签
隐藏标签提示
暗风险提示
买入按钮
禁用原因
```

推荐格式：

```text
A号年轻名校肉
进价：40｜基础价：50｜新鲜度：3 / 3
标签：[年轻] [名校] [? 履历风险]
暗风险：可能存在履历类风险
[买入]
```

## 11.4 隐藏标签显示规则

未揭示隐藏标签显示：

```text
[?]
```

```text
[水货] 已压制：残余风险 +9

```

## 18.9 UnknownRiskBreakdown 显示

未知风险必须单独显示，不能混入已知风险。

```text
未知风险：
- 未揭示隐藏标签：可能提高爆雷上限
- 暗风险存在：履历类风险可能导致事故升级
```

```text
未揭示隐藏标签：爆雷上限 +35
```

```text
预计售价已达到顾客预算上限。
当前爆雷区间最坏情况会触发严重事故。
商品已变质，售价下降且爆雷上升。
```

## 18.11 出售按钮位置

出售按钮放在 DealPreviewPanel 底部。

按钮文本：

```text
确认出售
```

如果处于 DAY_PROCESS，可显示 disabled：

```text
进入出售阶段后才能确认出售。
```

或允许在处理阶段直接出售。第一版推荐：

```text
处理阶段只预览，不确认出售。
出售阶段才允许确认出售。
```

## 18.12 出售按钮 enabled 条件

```text
DayState.phase == DAY_SELL
selectedProduct != null
selectedCustomer != null
selectedPricingMode != null
selectedProduct.status == inventory
selectedProduct.flags.sold == false
DealPreview.valid == true
```

## 18.13 出售按钮 disabledReason

| 条件 | 文案 |
|---|---|
| 非出售阶段 | 进入出售阶段后才能确认出售。 |
| 未选择商品 | 请先选择商品。 |
| 未选择顾客 | 请先选择顾客。 |
| 未选择定价 | 请先选择定价方式。 |
| 商品已售出 | 该商品已售出。 |
| 预览失败 | 交易预览计算失败，无法出售。 |
| 定价方式不可用 | 当前定价方式不可用于该商品。 |

## 18.14 验收标准

```text
任何选择或操作变化后，交易预览必须刷新。
存在未知信息时必须显示风险区间，而不是精确爆雷值。
没有未知信息时必须显示精确爆雷值。
priceBreakdown、riskBreakdown、unknownRiskBreakdown 至少可以展开查看。
确认出售按钮状态必须与实际可出售条件一致。
```

# 21. AccidentModal 事故弹窗

## 21.1 触发条件

交易结算后：

```text
DealResult.accidentLevel != none
```

## 21.2 必须显示字段

```text
事故标题
事故描述
最终爆雷值 finalRisk
基础事故等级 baseAccidentLevel
最终事故等级 finalAccidentLevel
成交收入 finalPrice
退款 refund
罚款 fine
信誉损失 reputationLoss
现金变化 cashDelta
累计利润变化 totalProfitGain
事故链条 accidentChain
主要风险来源
未知信息揭示结果，可选但不得过度泄露后续无关信息
确认按钮
```

## 21.3 推荐结构

```text
事故发生：履历背调被打穿

最终爆雷：87
基础事故：大事故
最终事故：严重事故（大厂 HR 风险容忍被突破：事故等级 +1）

成交收入：220
退款：-110
罚款：-10
现金变化：+100
累计利润：+70
信誉损失：-30

事故链条：
1. [名校] 提高售价，但带来履历风险。
2. [水货] 命中大厂 HR 雷区。
3. 今日新闻“名校水货事件发酵”使 [水货] 爆雷 +30。
4. 高价卖使爆雷 +15。
5. 履历暗风险在结算时爆发。
```

## 21.4 未知信息揭示

事故发生后，可以展示导致本单事故的隐藏信息。

允许：

```text
本单结算揭示：隐藏标签 [水货] 命中顾客雷区。
本单结算揭示：履历暗风险导致爆雷上升。
```

不允许：

```text
提前揭示其他未出售商品的隐藏标签或暗风险。
```

## 21.5 无事故时是否弹窗

第一版不需要无事故弹窗。

无事故交易用 Toast + 日志即可：

```text
成交成功，无事故。现金 +160，累计利润 +120。
```

## 21.6 事故后按钮

如果事故后未失败：

```text
[知道了]
```

点击后：

```text
关闭弹窗
刷新主界面
停留在 DAY_SELL
```

如果事故导致失败：

```text
[查看最终报告]
```

点击后：

```text
打开 RunReportModal
```

## 21.7 验收标准

```text
事故弹窗必须解释事故原因，而不是只扣数值。
事故弹窗中的现金、累计利润、信誉变化必须与 DealResult 一致。
事故链条必须显示主要风险来源。
```

如果当前天数 == 8：

```text

RunReportModal
```

## 22.9 验收标准

```text
最终现金：120

总交易：11 笔
事故：4 次
最大单笔利润：145
最大事故：大事故
```

```text
最终信誉：0 / 100

```

## 23.5 主要流派判断

第一版可使用简单计数：


| 最高类别 | 主要流派 |
|---|---|
| career | 大厂牛马流 |
| family | 稳定相亲流 |
| flow | MCN 发疯流 |
| mixed | 混合套利流 |

```text
[水货]
履历暗风险
高价卖
```

```text
暂无明显爆雷原因。
```

## 23.7 验收标准

```text
游戏结束时必须显示最终报告。
胜利 / 失败条件必须正确。
报告中的核心数值必须来自 RunReport，不得重新随意计算。
重新开始按钮必须能开启新局。
```

# 29. UI 与计算模块边界

## 29.1 UI 不直接计算核心结果

UI 不应在点击事件中手写售价、风险、事故公式。

UI 只调用：

```text
calculateDealPreview(context)
resolveDeal(context)
getButtonState(context)
```

## 29.2 UI 可以计算展示态

UI 可以计算：

```text
面板是否展开
按钮是否高亮
字段是否为空
文本是否折叠
日志筛选
```

## 29.3 交易预览数据来源

DealPreviewPanel 只读取：

```text
DayState.currentDealPreview
```

或调用 preview 函数后写回：

```text
DayState.currentDealPreview = calculateDealPreview(context)
```

不得从 DOM 文本反向读取交易数据。

## 29.4 结算数据来源

AccidentModal 和 RunReportModal 只读取：

```text
DealResult
AccidentInstance
RunReport
```

不得在弹窗里重新计算现金、利润或信誉。

# 30. 可访问性与可操作性要求

## 30.1 文字可读性

第一版建议：

```text
正文最小 14px
重要数值 16px 以上
按钮文字清晰
长文本可折叠
```

## 30.2 键盘可操作，可选但建议

建议至少支持：

```text
Tab 聚焦按钮
Enter 确认按钮
Esc 关闭可关闭弹窗
```

## 30.3 不依赖颜色

重要状态不能只靠颜色表达。

例如不要只用红色表示危险，还要写：

```text
危险
高危
必炸
现金不足
```

## 30.4 文本密度

由于本游戏信息量较大，推荐：

```text
卡片摘要常驻
详细 breakdown 折叠
事故链条弹窗展示
日志保留但可滚动
```

# 31. UI 文案规范

## 31.1 文案语气

第一版 UI 文案应保持：

```text
清楚
直接
略带黑色幽默
不影响规则理解
```

规则解释优先于玩梗。

## 31.2 数值文案格式

统一格式：

```text
现金 +100
现金 -20
累计利润 +120
信誉 -15
爆雷 +30
售价 ×1.3
风险区间 45–95
```

## 31.3 未知信息文案

正确：

```text
未知标签可能提高爆雷上限。
暗风险存在，具体类别未知。
该商品可能存在履历类暗风险。
```

错误：

```text
隐藏标签是水货。
实际暗风险 +35。
这个商品一定会背调爆炸。
```

除非信息已经在结算或揭示后可见。

# 32. UI 验收清单

## 32.1 页面结构验收

必须满足：

```text
顶部状态栏常驻。
阶段提示清楚。
市场新闻可见。
库存和商品详情可见。
顾客订单可见。
处理阶段可见手牌、基础操作、定价和交易预览。
出售阶段可确认交易。
日志区可查看最近操作。
```

## 32.2 阶段交互验收

必须满足：

```text
玩家可以从开始新局一路推进到第 8 天。
每日阶段不会卡死。
阶段按钮不会跳错阶段。
出售阶段可以返回处理阶段，但不能返回更早阶段。
收店奖励选择后进入下一天或最终报告。
```

## 32.3 商品 UI 验收

必须满足：

```text
商品候选显示进价、基础价、标签、隐藏提示、暗风险提示。
库存商品可选中。
商品详情显示真实可见信息。
未揭示隐藏标签不泄露。
已售商品不可再次出售或加工。
```

## 32.4 顾客 UI 验收

必须满足：

```text
顾客卡显示预算、风险容忍、喜欢标签、雷区标签、暗风险敏感和特殊规则。
选择顾客后交易预览刷新。
```

## 32.5 操作 UI 验收

必须满足：

```text
鉴定、洗标、包装、公关按钮状态正确。
手牌使用按钮状态正确。
定价按钮状态正确。
所有 disabled 状态有原因。
操作后状态栏、商品详情、交易预览和日志更新。
```

## 32.6 交易预览验收

必须满足：

```text
显示预计售价。
显示预计利润。
显示预算上限。
显示爆雷值或爆雷区间。
显示事故预测。
显示主要加价来源。
显示主要风险来源。
显示未知风险来源。
存在未知信息时不显示精确爆雷。
不存在未知信息时显示精确爆雷。
```

## 32.7 事故弹窗验收

必须满足：

```text
事故发生时弹窗出现。
弹窗显示最终爆雷、事故等级、退款、罚款、信誉损失、现金变化、累计利润变化。
弹窗显示事故链条。
事故导致失败时能进入最终报告。
```

## 32.8 奖励弹窗验收

必须满足：

```text
每日收店显示 3 个奖励。
现金不足奖励不可选。
选择奖励后只获得一个。
奖励效果进入牌组、被动、货源或资源状态。
```

## 32.9 最终报告验收

必须满足：

```text
胜利或失败显示正确。
最终累计利润、现金、信誉正确。
总事故次数正确。
主要流派和主要爆雷原因可显示。
重新开始按钮可用。
```

## 32.10 技术基础验收

必须满足：

```text
UI 不出现 NaN、undefined、null。
核心计算不写在 DOM 事件里。
所有主要操作写入日志。
按钮状态和实际 action 前置条件一致。
```
