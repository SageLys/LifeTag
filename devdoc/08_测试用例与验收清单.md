# 08_测试用例与验收清单

文档编号：08  
文档名称：测试用例与验收清单  
项目名称：《人生标签交易所：牛马肉铺》HTML 快速验证原型  
对应策划案版本：核心策划案 v0.5  
文档版本：v0.1  
用途：定义 HTML 原型第一版的测试范围、测试方法、固定测试局、功能验收清单、计算验收清单、UI 验收清单、Debug 验收、回归测试与发布前检查。  
适用对象：游戏设计者、前端开发者、AI Agent / Codex、测试者。

---

# 1. 文档目的

本文档用于回答以下问题：

1. HTML 原型第一版完成后，怎样判断它真的可玩；
2. 怎样判断它不是“页面能点”，而是完整实现了核心玩法闭环；
3. 怎样测试每日流程是否正确；
4. 怎样测试现金、累计利润、信誉、行动点、库存是否正确变化；
5. 怎样测试售价、爆雷、事故、退款、罚款、累计利润是否正确；
6. 怎样测试隐藏标签和暗风险没有被错误显示；
7. 怎样测试 UI 按钮的 enabled / disabled 状态；
8. 怎样测试三条核心流派是否至少能跑通；
9. 怎样测试 Debug 面板和固定测试局是否可用于后续迭代；
10. 怎样判断当前版本可以交给外部测试者试玩。

本文档不负责：

- 重新定义玩法规则；
- 重新定义数据结构；
- 重新定义 UI 布局；
- 重新设计数值平衡；
- 编写正式版自动化测试框架；
- 编写正式 QA 报告。

本文档负责：

```text
把第一版 HTML 原型的“完成标准”写成可执行、可复查、可复现的验收项目。
```

# 2. 测试总原则

## 2.1 第一版测试目标

第一版测试不追求最终平衡，而是验证：

```text
系统能不能跑通；
核心规则有没有错；
玩家能不能理解；
事故能不能复盘；
构筑成长有没有基础反馈；
AI Agent / 开发者后续改动会不会破坏核心闭环。
```

## 2.2 测试优先级

所有测试分为 4 个优先级。

|优先级|含义|是否必须通过|
|---|---|---|
|P0|核心闭环测试|必须通过，否则不能称为可玩原型|
|P1|强烈建议测试|建议通过，否则试玩质量明显下降|
|P2|扩展测试|后续迭代测试，可暂时跳过|
|Debug|开发辅助测试|建议通过，否则后续排错困难|

## 2.3 缺陷严重度

|严重度|定义|处理要求|
|---|---|---|
|S0 阻塞|游戏无法启动、无法进入新局、流程卡死、控制台持续报错|必须立即修复|
|S1 核心错误|资源计算、交易结算、事故判定、胜负判定错误|必须在交付前修复|
|S2 重要错误|UI 显示错误、按钮状态错误、日志缺失、局部流程不清楚|建议交付前修复|
|S3 轻微错误|文案错别字、排版瑕疵、非核心提示不清楚|可记录后续修复|
|S4 优化建议|数值平衡、体验节奏、美术表现、后续功能建议|不阻塞当前版本|

## 2.4 测试通过标准

一个测试用例通过，必须满足：

```text
前置条件正确；
执行步骤可复现；
实际结果与预期结果一致；
关键数据变化正确；
UI 显示与运行时状态一致；
控制台无新增错误；
日志中能追踪关键操作。
```

## 2.5 随机性测试原则

本游戏允许随机生成：

```text
商品候选
隐藏标签
暗风险
顾客订单
市场新闻
抽牌
收店奖励
```

但测试时必须支持：

```text
固定 seed
固定测试场景
固定测试商品
固定测试顾客
固定测试新闻
固定测试手牌
```

否则无法验算售价、爆雷和事故。

## 2.6 核心禁止项

任何版本都不得出现以下情况：

```text
事故是否发生由随机骰子决定。
现金被当作通关目标。
累计利润被洗标、包装、公关等支出扣减。
普通鉴定完全揭示暗风险。
存在未知信息时 UI 仍显示单一精确爆雷值。
已售商品还能再次出售。
现金不足时仍能主动付费操作。
行动点不足时仍能使用消耗行动点的操作。
盲盒价在无未知信息时仍可使用。
```


测试前应确认：

```text
1. /data/ 下所有 JSON 文件存在；

4. 点击“开始新局”可以进入第 1 天；
5. Debug 面板可以开启或隐藏；
6. 当前版本号记录在 README 或页面角落。
```

```text
TEST_类型_序号
```

推荐类型：

|类型|含义|
|---|---|
|BOOT|启动与数据加载|
|FLOW|流程与阶段推进|
|STATE|状态与资源|
|DATA|配置与数据引用|
|PRODUCT|商品系统|
|CUSTOMER|顾客系统|
|DECK|牌组与卡牌|
|ACTION|基础操作|
|PRICE|售价计算|
|RISK|爆雷计算|
|ACCIDENT|事故结算|
|REWARD|收店奖励|
|UI|界面与交互|
|SAVE|存档与读档|
|DEBUG|Debug 工具|
|RUN|完整局测试|
|REG|回归测试|

示例：

```text
TEST_PRICE_001：基础售价计算
TEST_RISK_004：未揭示隐藏标签导致爆雷区间
TEST_ACCIDENT_003：严重事故导致信誉归零失败
```

# 5. 总体验收标准

## 5.1 可玩闭环验收

第一版必须满足：

```text
玩家可以从第 1 天开始新局；
每天能经历开店、进货、接单、抽牌、处理、出售、结算、收店；
玩家能在第 8 天结束并进入最终报告；
胜利 / 失败条件能够正确触发；
全过程不需要刷新页面；
全过程不需要手动改数据；
全过程控制台不出现阻塞错误。
```

## 5.2 核心体验验收

第一版必须能让测试者完成以下行为：

```text
看懂今日市场新闻；
根据商品标签和顾客偏好选择买货；
识别隐藏标签和暗风险带来的未知；
选择鉴定、洗标、包装、公关或出牌；
查看交易预览；
理解售价为什么上涨；
理解风险为什么升高；
在稳卖和赌一把之间做选择；
出售后看到收益、事故、信誉变化；
每日收店选择成长奖励；
最终看到经营报告。
```

## 5.3 文档一致性验收

实现必须符合：

```text
00_HTML原型范围说明.md
01_核心玩法流程规格.md
02_系统规则规格.md
03_数据结构规格.md
04_首版配置表说明.md
05_售价爆雷事故计算规格.md
06_UI页面与交互规格.md
07_HTML技术实现规格.md
```

若实现与文档冲突，以较新的规格文档为准。若仍不明确，必须在代码注释或 TODO 中标注。

# 30. 玩法验证指标

第一版 HTML 原型完成后，建议至少找 3–5 名测试者试玩。

## 30.1 必看定性指标

|问题|观察标准|
|---|---|
|玩家是否知道每天要做什么|是否频繁问“现在该点哪里”|
|玩家是否理解现金不是分数|是否愿意花现金买成长|
|玩家是否理解累计利润目标|是否关注 500 目标进度|
|玩家是否理解风险区间|是否知道未知信息在造成区间|
|玩家是否会主动赌|是否使用高价卖 / 盲盒价|
|玩家是否能复盘事故|事故后能否说出主要原因|
|玩家是否形成流派|是否围绕某类顾客 / 标签构筑|
|玩家是否觉得只是匹配|如果觉得只是匹配，说明系统表达不足|

## 30.2 建议量化记录

|指标|记录方式|
|---|---|
|平均游玩时长|分钟|
|完整通关率|完成第 8 天人数 / 总人数|
|胜利率|胜利人数 / 完整局人数|
|平均事故次数|每局事故数|
|盲盒价使用率|每局盲盒价次数|
|付费奖励选择率|付费奖励次数 / 总奖励次数|
|现金低于 30 的次数|衡量现金压力|
|玩家主动鉴定次数|衡量信息系统参与度|
|玩家主动洗标次数|衡量风险处理参与度|
|最大单笔利润|衡量爽点峰值|

## 30.3 判断是否需要改设计

如果出现以下情况，说明需要回到设计文档修改：

```text
多数玩家不理解现金和累计利润区别；
多数玩家不看交易预览直接出售；
多数玩家不理解事故原因；
多数玩家从不使用盲盒价；
多数玩家从不购买付费奖励；
多数玩家觉得商品只是标签匹配；
事故过多导致频繁失败但玩家不知道为什么；
事故过少导致风险系统没有存在感；
三条流派中只有一条明显可玩；
收店奖励无法改变后续策略。
```

# 35. 总结

本测试文档的核心目标是确保 HTML 原型不是“规则写在文档里，页面只是长得像游戏”，而是真的完成以下闭环：

```text
看新闻
→ 买货
→ 看顾客
→ 抽牌
→ 加工
→ 预览收益与风险
→ 出售
→ 爆雷或赚钱
→ 复盘事故
→ 收店成长
→ 推进下一天
→ 第 8 天结算
```

第一版最重要的验收标准不是数值是否完美，而是：

```text
玩家能理解自己为什么赚钱；
玩家能理解自己为什么爆雷；
玩家能通过现金、行动点、卡牌、被动和货源倾向改变下一天的策略；
开发者能通过固定测试局复现并修复问题。
```

只要这些成立，HTML 原型就完成了它的核心任务：

```text
验证《人生标签交易所：牛马肉铺》的核心玩法是否值得继续扩展到 Unity 正式版。
```
